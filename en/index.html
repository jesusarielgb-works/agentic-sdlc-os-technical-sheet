Agentic SDLC OS

Agentic SDLC Orchestration System: a private agentic ecosystem that coordinates artificial intelligence agents across every phase of the software lifecycle. Its controls are verifiable, and the final decision is always made by a person.

What it is

Agentic SDLC OS coordinates specialized artificial intelligence agents across the software lifecycle: discovery, design, build, quality and release. Each agent has a bounded responsibility, declared inputs, expected outputs and validation criteria.

Between one phase and the next there is a quality gate. If an agent rejects the work, it goes back with feedback. If a governance condition fails, the flow stops.

In the name, OS stands for Orchestration System: the layer that coordinates agents, phases, artifacts, gates and traceability. It is not an operating system.

It is a personal work of its author, who uses it wherever it is needed: in software development, in teaching or in any other project.

What it offers

  • A governed flow, from requirements to release.
  • Artifact contracts and handoff rules between agents.
  • Automatic halt conditions.
  • Quality gates and rejection loops.
  • Control over the context each agent reads, to reduce cost and errors.
  • Resumable execution and traceable evidence.

What it is not

  • A collection of loose prompts.
  • A single agent that does everything.
  • A system that reads entire repositories without scope control.
  • A replacement for a person's technical accountability.

How to verify a document

Every assessment is delivered with two fingerprint files. HUELLAS-SHA256.txt holds the fingerprint of each PDF. EVIDENCIA-SHA256.txt holds the fingerprint of each evidence file, and the PDF's signature includes the fingerprint of that list. If a single byte changes, verification fails.

sha256sum -c HUELLAS-SHA256.txt
sha256sum EVIDENCIA-SHA256.txt   # must match the fingerprint printed in the signature

A PDF cannot contain its own fingerprint, because writing it would change the file. That is why the signature carries the fingerprint of the evidence, and the PDFs' fingerprints go in a separate file.

How we got here

This ecosystem did not start as a product. It grew on two pillars that feed each other: teaching, which demands explaining and assessing with judgment, and technical work, which demands delivering and answering for what is delivered.

Teaching

  • Training software analysis and development technologists, with real team projects.
  • Rubrics in which every criterion states what is checked and how it is verified.
  • End-to-end assessment: each team's system is brought up and used, not just read.
  • Improvement plans with evidence, deadlines and a defense.
  • Learning and research guides built on institutional formats.

Technical work

  • Governance frameworks for microservices, monoliths and mobile, released under the MIT license.
  • Web applications deployed to production, with end-to-end tests before every release.
  • Microservices, relational databases and versioned migrations in industry environments.
  • Environment-based delivery: development, testing, staging and production.
  • Agent orchestration with gates, halts and traceability: this ecosystem.

The journey, in four stretches:

Teach

Explaining a good practice forces you to understand why it exists, not just how to apply it.

Document

What was repeated in every course ended up written down, organized and open to anyone.

Build

In industry, the same principles met deadlines, production and real consequences.

Orchestrate

When agents arrived, the question stopped being what they can do and became who answers for what they do.

The answer to that question shapes everything else.

Declared limits

  • Artificial intelligence assists: it gathers evidence, proposes and verifies. It does not grade on its own.
  • Current maturity is partial L2: the flow is governed and traceable, but it does not yet have all the controls of a higher level.
  • This sheet describes what the ecosystem does, not how it is built inside.
  • An assessment relies only on what can be verified. Whatever could not be checked is written down as a limit in each report.
